# Ship

Own only the landing the user authorized.

1. The user invoking this skill by name, or asking to merge, land or ship, is
   the merge authority: land without asking whether to. Take the work they
   name; with none named, the work this conversation built or the current
   branch's open pull request. Ask only if no target or several fit. Your own
   choice of this skill, ownership or a budget never counts. Honor holds,
   later stops and operator-reserved gates.
2. Require [verify](../verify/SKILL.md)'s independent passing verdict on the
   current revision, or a documented exemption under its review scope. Required checks
   and safety evidence must pass; unresolved blockers or unavailable review
   stop landing: report them, do not ask for approval. Every finding, a bot's
   included, has a fix or a written reason. Confirm host mergeability and
   dependency readiness.
3. Land only the contiguous authorized, verified run from the lowest unmerged
   dependency, one request at a time, using the project's delivery mechanism.
   Do not merge a child into an unlanded parent or arm descendants. Changed
   revisions or bases require fresh checks and a current passing verdict or
   documented exemption under verify, including its carry-forward rules.
4. Confirm each landed result in the intended destination, not merely that a
   merge was requested. Reinspect the next request after each landing. If the
   remote outcome is unknown, inspect it before retrying. Stop at the first gap.
5. Report what actually landed, its revision and destination, remaining work
   and limits. Preserve unlanded branches and perform prescribed local cleanup.

Do not arm automatic merging without explicit merge-when-ready authority and
gates that preserve the verified revision. Merge permission does not authorize
deployment, destructive operations or unrelated work. Planning and help questions
explain this process without executing it; a stop instruction prevents writes.

# Verify

Both roles read the whole diff, delegated work too, and the
[rubric](references/review-rubric.md), never a summary.

## Author

1. Before editing, write checks on the real surface. A bug gets a failing check first.
2. Run them first on the real artifact; keep deciding lines.
   Green tests do not prove the contract.
3. Apply [review scope](references/review-scope.md). Unless exempt, ask
   one fresh read-only verifier. Without one, report unverified.
4. Give it the task, checks and revision range, not your conclusions;
   for a re-review, the change since the last verdict, what it affects
   and open findings.
5. Re-rank findings. Fix blockers and shoulds with the cheapest check
   catching them again; rerun affected checks. Decline nits without edits or another round.
   [Carry-forward](references/carry-forward.md) governs fixes.
   Deliver only with every required check and safety fact proven on this
   revision, a fresh pass or valid exemption, no blocker or should open.
6. Open after two rounds: stop and rethink the approach or scope.
   At most two more; still open, stop delivery, report both sides.

## Verifier

- Run every check yourself; reproduce a failure, suspecting your
  method first. Answer each pass, issues or not checked, with deciding
  lines; unrun is not checked.
- Name the fact its safety rests on; prove it on the real code or mark
  it unproven.
- Try to break it: inputs, failure paths, callers, what the diff
  omits. A base defect is the base's unless the change copies or newly
  reaches it.
- Show what reaches each issue; rank it. Blocker: the intended case is
  wrong. Should: ordinary use, a caller, stored or imported data, a race
  or a setting reaches it. Nit: nothing shown reaches it, contrived input
  giving only a wrong result or warning, wording, extra tests or guards,
  small costs, what only later code makes. Data loss, security or a trust
  boundary is never a nit.
- Name the revision and patch judged. Change nothing.

# Full autopilot

Own delivery inside an explicit boundary, not an unlimited backlog.

- Establish the queue, dependencies, completion checks and operator-held
  items before execution. “Autopilot” or “full send” on named work authorizes
  both the work and its landing, and nothing then waits for the user's
  approval; “keep going” or a budget does neither. If the work is unclear,
  land nothing. Plan/help requests do not execute.
- Compose [build](../build/SKILL.md), [babysit](../babysit/SKILL.md) and
  [ship](../ship/SKILL.md). Their boundaries and [verify](../verify/SKILL.md)'s
  independent current-revision gate still apply to each item; autonomy removes
  prompts and the user's approval, never evidence or the host's protections.
- Before any code or brief, complete build's design step. Give each
  participant a bounded change, ownership and that note. The coordinator owns
  dependency order and delivery. Land only the authorized verified frontier;
  do not skip blocked prerequisites or delegate away an operator-held decision.
- Keep a [show-me-your-work](../show-me-your-work/SKILL.md) decision log.
  Track progress by artifacts and current checks, not reassuring status text.
  Keep independent authorized work moving when one item is blocked. Stop at
  queue completion, an authority boundary, or an explicit stop. On stop, place
  all participants on a no-writes hold and report issued operations' known state.
- Report each landed revision and destination, remaining requests and gates,
  evidence and limits. Release only project-prescribed local artifacts.

Merge authority is not permission to deploy, delete data, override protections
or perform unrelated irreversible actions. Never expand the authorized queue
merely to consume spare capacity.

# Orchestrate

You run the program, never the code. Assign work and check its results. One coordinator thread owns a
multi-day program of many, often stacked, pull requests.
[Autopilot-full](../autopilot-full/SKILL.md) handles a bounded queue in one
session; [swarm](../swarm/SKILL.md) handles parallel independent parts of one
task. 

Use the harness's delegation. Keep goals, checks, dependencies, standing orders,
ownership, briefs, PR links, revisions, verdicts and blockers in a durable notes file in the repo or tracker. Keep the decision
trail through [show-me-your-work](../show-me-your-work/SKILL.md). On pickup,
read those records and reconcile live work before launching replacements.
Use event subscriptions or watchers if the harness has them. Do not build
orchestration scripts, run polling loops or relay routine status between agents.
Unavailable delegation is a blocker; do not code yourself.

## Authority and delivery

Invoking orchestrate grants landing authority for the program, like
[autopilot-full](../autopilot-full/SKILL.md). Fully drive every PR through
build, verification, readiness and landing to the program's goal. Nothing
waits for the user's approval to merge. The owner lands only with a passing
independent verdict on the current head, required checks and honored holds,
through [ship](../ship/SKILL.md)'s gates. Resolve failed gates by re-delegating,
not asking for approval. You never merge or edit code.

Before the first unit, anticipate product, preference, irreversible-step,
scope or risk decisions that could later hold a merge. Ask all known questions
early in one message, with stated defaults. Proceed on those defaults for
unanswered questions within existing authority. Defaults never grant excluded
permissions or override holds. Mid-program ask only for a genuinely new such
decision, never whether to merge or keep going.

Explicit "don't merge" or "I'll land it" instructions stop owners at
merge-ready. Authority excludes deployment, destructive operations and work
outside the program. Planning/help explains without executing.

Owners compose [build](../build/SKILL.md), [babysit](../babysit/SKILL.md) for
readiness, and [verify](../verify/SKILL.md) for independent current-revision
evidence. Use swarm for independent parts; delegation never expands authority.

## Topology

- One owner per PR, the only writer of its branch, carries it from build to
  the authorized endpoint. Only that owner pushes, rebases or retargets it.
  Closing or retargeting a base can orphan children and needs your call.
  You never author or edit code. Give conflicts, chain rebases and fixes
  to owners.
- A fresh worker for each independent task. Its kickoff is self-contained,
  including each upstream report it depends on in full. Workers cannot see
  siblings. Choose an execution environment with the required code, runtime
  and access; work needing local transcripts, a simulator or local-only
  authentication stays where those exist. Model, effort and speed choice
  follow the user's routing rules.
- Add a sub-coordinator only for an area with many parallel workers. It owns
  their kickoffs and sends one rollup, never raw reports. Stop at three levels:
  you, sub-coordinators, workers. Keep about ten workers in flight per
  coordinator, subject to available capacity; refill as each finishes.
- When new work needs a worker's built state, use the harness's state-preserving
  delegation if available, otherwise explicitly hand off the required state.
  Message a worker only for a follow-up on the same work, never to check on it.
- Each PR gets a fresh read-only verifier who is not its author, from a
  different provider or model family if available. Apply verify's revision
  and carry-forward rules. Green checks alone never authorize landing.
- Start with one unit through kickoff, owner, verifier and merge before
  fan-out, or merge-ready when the user explicitly reserves landing. On cheap similar
  units this pilot tests the kickoff before a mistake multiplies.

## Supervision

- Each kickoff names the goal, allowed and forbidden paths, exclusive branch
  ownership, forbidden actions and the evidence proving completion, such as
  checks and expected output or an artifact. Without that evidence the unit
  is not scoped. Include dependencies, standing orders and landing authority.
- Read the diff or artifact, not only the summary. Apply verify when revisions change; a type check alone is insufficient. Sample sub-coordinator
  kickoffs while work runs and fix instructions when needed.
- Send back work that drifts or grows beyond the request. Keep fixes that
  block the program and park the rest as follow-ups.
- Check every PR's live state before reporting it. Account for each worker
  as done, replaced or absorbed into another worker's scope. Do not wake workers for status.
- Stop or replace stalled or looping workers. Judge artifacts and PR activity,
  not status prose. Retry by cause: smaller scope after a context or memory
  limit, the same kickoff after a dropped connection, a different suitable
  model after a tool error under routing rules. After two retries drop the
  unit and replan. Reconcile late results against the current PR state and
  give unique findings to a fresh worker.
- Ask only for a real decision or blocker under the early-question rule.
  Rebase mechanics, retries, flaky checks and review triage stay with owners.
  Replan dead ends and keep independent work moving.

## Reply

Report what landed against the goal, each PR's live state and verdict with
its link, what was dropped and why, and decisions waiting on the user.
Distinguish merge-ready work from landed work. Link notes and trail. Report unavailable evidence as unknown.
