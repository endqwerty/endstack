# Ship

Own only the landing the user authorized.

1. Identify the exact work and destination, and the instruction granting merge
   authority. An explicit “ship this pull request”, or “autopilot” or “full
   send” on it, counts; selecting this skill, ownership or a budget request
   alone does not. Honor holds, later stops and operator-reserved gates. If
   the scope is unclear, do not land anything.
2. Require [verify](../verify/SKILL.md)'s independent passing verdict on the
   current revision, or a documented exemption under its review scope. Required checks
   and safety evidence must pass; unresolved blockers or unavailable review
   stop landing. Every finding on it, a bot's included, has a fix or a
   written reason. Confirm current host mergeability and dependency readiness.
3. Land only the contiguous authorized, verified run from the lowest unmerged
   dependency, one request at a time, using the project's delivery mechanism.
   Do not merge a child into an unlanded parent or arm descendants. Changed
   revisions or bases require fresh checks and a current passing verdict or
   documented exemption under verify, including its carry-forward rules.
4. Confirm each landed result in the intended destination, not merely that a
   merge was requested. Reinspect the next request after each landing. If the
   remote outcome is unknown, inspect it before retrying. Stop at the first gap.
5. Report what actually landed, its revision and destination, remaining work
   and limits. Preserve unlanded branches and perform prescribed local cleanup.

Do not arm automatic merging without explicit merge-when-ready authority and
gates that preserve the verified revision. Merge permission does not authorize
deployment, destructive operations or unrelated work. Planning and help requests
explain this process without executing it; a stop instruction prevents writes.

# Verify

Both roles read the whole diff, delegated work too, and the
[rubric](references/review-rubric.md), never a summary.

## Author

1. Before editing, write checks on the real surface. A bug gets a failing check first.
2. Run them first on the real artifact; keep deciding lines.
   Green tests do not prove the contract.
3. Apply [review scope](references/review-scope.md). Unless exempt, ask
   one fresh read-only verifier. Without one, report unverified.
4. Give it the task, checks and revision range, not your conclusions;
   for a re-review, the change since the last verdict, what it affects
   and open findings.
5. Re-rank findings. Fix blockers and shoulds with the cheapest check
   catching them again; rerun affected checks. Decline nits without edits or another round.
   [Carry-forward](references/carry-forward.md) governs fixes.
   Deliver only with every required check and safety fact proven on this
   revision, a fresh pass or valid exemption, no blocker or should open.
6. Open after two rounds: stop and rethink the approach or scope.
   At most two more; still open, stop delivery, report both sides.

## Verifier

- Run every check yourself; reproduce a failure, suspecting your
  method first. Answer each pass, issues or not checked, with deciding
  lines; unrun is not checked.
- Name the fact its safety rests on; prove it on the real code or mark
  it unproven.
- Try to break it: inputs, failure paths, callers, what the diff
  omits. A base defect is the base's unless the change copies or newly
  reaches it.
- Show what reaches each issue; rank it. Blocker: the intended case is
  wrong. Should: ordinary use, a caller, stored or imported data, a race
  or a setting reaches it. Nit: nothing shown reaches it, contrived input
  giving only a wrong result or warning, wording, extra tests or guards,
  small costs, what only later code makes. Data loss, security or a trust
  boundary is never a nit.
- Name the revision and patch judged. Change nothing.
